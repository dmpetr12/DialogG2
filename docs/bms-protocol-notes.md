# BMS батареи: заметки по протоколу

Источник: `C:\Users\Петр\Desktop\Аварийный шкаф\BMS батареи.pdf`

## Интерфейс

- Протокол Jiabaida software board для RS485/RS232/UART.
- Это не Modbus RTU: кадр начинается с `0xDD`, запрос чтения содержит `0xA5`, ответ содержит команду и статус.
- Скорость по документу: 9600 bps или заказная.
- 16-битные данные идут big-endian.
- BMS может спать; первый запрос после сна может не получить ответ, запрос нужно повторить.

## Кадр

Запрос чтения:

```text
DD A5 command length data checksumHi checksumLo 77
```

Для штатных запросов данных нет, длина `0`.

```text
basic info:    DD A5 03 00 FF FD 77
cell voltages: DD A5 04 00 FF FC 77
```

Ответ:

```text
DD command status length data [callbackId] checksumHi checksumLo 77
```

Checksum считается как двухбайтное дополнение суммы `status + length + data`.
`callbackId`, если он есть, BMS возвращает обратно, но в checksum он не входит.

## Команды для оперативного снимка

- `0x03` - basic information/status.
- `0x04` - напряжения ячеек.
- `0x05` - аппаратная версия / модель платы.
- `0xAA` - статистика срабатываний защит, полезно для диагностики, но не обязательно для главного снимка.

## Данные из `0x03`

- Полное напряжение батареи, единица 10 mV.
- Ток батареи, знаковое значение, единица 10 mA или 100 mA в зависимости от флага FET.
- Остаточная ёмкость, единица 10 mAh или 100 mAh.
- Номинальная ёмкость, единица 10 mAh или 100 mAh.
- Количество циклов.
- Дата производства.
- Состояние балансировки ячеек 1-16 и 17-32.
- Статус защит, 16 бит.
- Версия ПО.
- RSOC, процент остаточной ёмкости.
- Состояние FET/MOS:
  - bit0 - charge MOS;
  - bit1 - discharge MOS;
  - bit2 - current limiting module;
  - bit3 - heating;
  - bit7 - единицы тока/ёмкости.
- Количество ячеек.
- Количество NTC.
- Температуры NTC, 0.1 K, пересчёт в °C: `raw - 2731`.
- Влажность, 1%.
- Статус предупреждений, 16 бит.
- Полная зарядная ёмкость.
- Остаточная ёмкость.
- Ток балансировки, mA.

## Защиты

`protectionStatus`:

- bit0 - перенапряжение ячейки.
- bit1 - пониженное напряжение ячейки.
- bit2 - перенапряжение всей батареи.
- bit3 - пониженное напряжение всей батареи.
- bit4 - перегрев при заряде.
- bit5 - низкая температура при заряде.
- bit6 - перегрев при разряде.
- bit7 - низкая температура при разряде.
- bit8 - сверхток заряда.
- bit9 - сверхток разряда.
- bit10 - короткое замыкание.
- bit11 - ошибка front-end detection IC.
- bit12 - software lock MOS.
- bit13 - пробой charge MOS.
- bit14 - пробой discharge MOS.
- bit15 - резерв.

## Предупреждения

`alarmStatus`:

- bit0 - высокое напряжение ячейки.
- bit1 - низкое напряжение ячейки.
- bit2 - высокое напряжение всей батареи.
- bit3 - низкое напряжение всей батареи.
- bit4 - высокая температура заряда.
- bit5 - низкая температура заряда.
- bit6 - высокая температура разряда.
- bit7 - низкая температура разряда.
- bit8 - высокий ток заряда.
- bit9 - высокий ток разряда.
- bit10 - большой разброс напряжений ячеек.
- bit11 - низкая ёмкость.

## Данные из `0x04`

- Массив напряжений ячеек.
- Каждая ячейка: 2 байта, mV.
- Количество значений равно числу ячеек.

## Эксплуатационный `BatterySnapshot`

На главный экран:

- `socPercent`
- `stateText`

На экран АКБ:

- `voltage`, `current`
- `remainingCapacityAh`, `nominalCapacityAh`, `fullChargeCapacityAh`
- `cycleCount`
- `cellVoltages`
- `minCellVoltage`, `maxCellVoltage`, `cellVoltageDelta`
- `temperatures`, `minTemperature`, `maxTemperature`
- `chargeAllowed`, `dischargeAllowed`
- `balancingActive`, `heatingActive`
- `faults`, `warnings`
- `protectionStatusRaw`, `alarmStatusRaw`

Паспортные данные вроде версии платы и ПО электрику в эксплуатации не нужны; их можно читать только для сервисной диагностики, если понадобится.

## Рекомендуемый опрос

- `0x03` basic info: раз в 1-2 секунды.
- `0x04` cell voltages: раз в 5-10 секунд или при открытии экрана АКБ.
- `0x05` version: не нужен в штатной эксплуатации.
- `0xAA` protection counters: редко, по сервисному запросу.

Так как батарея одна, такой опрос не должен заметно нагружать Modbus RTU. В драйвере нужно учитывать сон BMS: первый запрос после сна может не получить ответ, поэтому нужен повтор и состояние `Нет связи` только после нескольких ошибок подряд.

## Реализация в коде

Низкоуровневый протокол вынесен в `JbdBmsProtocol`:

- `buildReadCommand(0x03)` и `buildReadCommand(0x04)` собирают кадры запроса.
- `parseResponse(...)` проверяет заголовок, конец кадра, длину и checksum.
- `decodeBasicInfo(...)` переводит payload команды `0x03` в `BatterySnapshot`.
- `applyCellVoltages(...)` добавляет напряжения ячеек из команды `0x04` в `BatterySnapshot`.

Живой serial-опрос BMS делает `MeteringBusController`, а не старый `ModbusController`, потому что протокол BMS пакетный Jiabaida/JBD, а не Modbus RTU.
Так как BMS сидит на той же физической измерительной шине, `MeteringBusController` владеет одним `QSerialPort` и чередует Modbus RTU-запросы измерителям с raw JBD-запросами BMS.
